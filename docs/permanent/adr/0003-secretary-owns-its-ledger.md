# 0003. 秘書が独自の台帳を持ち、既存のタスク管理サービスを台帳にしない

- Status: accepted
- Date: 2026-09-04
- Deciders: リポジトリ所有者

## Context

秘書の目的は抜け漏れの棚卸しであり、3つの情報源を横断して「まだ終わっていないもの」を
拾い切ることにある。情報源はそれぞれ状態の持ち方が異なり、共通の器が要る。

既存のタスク管理サービスには既にタスクがあり、さらに日次の記録タスクの本文に、手書きの
やり残しリストが維持されていた。実データを見ると、このリストは日をまたいで複製されながら
持ち回られており、事実上これが現行の台帳として機能していた。

対案は2つあった。

既存サービスを台帳とする案。二重管理が起きず、他端末との同期も共有も自然に解決する。
ただし、セッションや会議メモから抽出される項目は粒度が細かく、それらをすべて書き込むと
既存の運用をノイズで埋める。抽出の誤りがそのまま他人から見える場所に出る問題もある。

台帳を持たず毎回再生成する案。古い情報が残らず実装も最小になる。しかし「これはもう
対応済み」という事実を記録できないため、同じ項目が毎回出続ける。棚卸しを目的とする以上、
消せないことは致命的である。

## Decision

秘書は独自の台帳を持つ。既存のタスク管理サービス、セッション、会議メモはすべて入力として
扱う。

台帳の性質は次のとおり。

- 1レコード = 1タスク。出所（種別と参照先）を属性として持つ
- 再収集で増殖しないよう、出所と正規化したタイトルから決定的な識別子を導出する
- 人がつけた状態を再収集で上書きしない。完了にしたものが翌日の収集で未完了に戻ると
  台帳が信用できなくなるため

## Consequences

- 3つの情報源を同じ形に正規化でき、横断した棚卸しが成立する
- 既存サービスとの二重管理になる。どちらを正とするかを運用で決める必要が残る
- 台帳のスキーマは後から変えにくい。粒度の変更は破壊的変更になる
- 出所をまたぐ重複（同じ用件が会議と既存サービスの両方に存在する場合）は、識別子が
  異なるため自動では統合されない。別途の突合が要る
