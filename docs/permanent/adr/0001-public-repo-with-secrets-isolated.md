# 0001. 秘書のコードを公開リポジトリに置き、非公開情報をホーム配下へ隔離する

- Status: accepted
- Date: 2026-09-04
- Deciders: リポジトリ所有者

## Context

タスク秘書は3つの情報源を横断する。Claude Code のセッション、カレンダーと
自動生成された会議メモ、そしてタスク管理サービス上のタスクである。後ろ2つには
社内の非公開情報が含まれる。

このリポジトリは公開されている。既存の自作ツール2本も同じ場所にあり、秘書もそこへ
並べるのが導線としては自然だった。一方で、過去に公開リポジトリへ非公開情報を含めて
しまった経緯があり、同じ場所を選ぶこと自体が争点になった。

対案は2つあった。設定配布用の非公開リポジトリに置く案と、秘書専用の非公開リポジトリを
新設する案である。前者は配布経路が1本で済むが、全メンバーの開発環境が依存するリポジトリに
アプリケーションの変更を継続的に入れることになる。後者は境界が明確だが、フックとスキルの
定義だけは配布用リポジトリ側に残るため、完全な分離にはならない。

判断の分かれ目は「何が実際に漏れるのか」だった。整理すると、コード自体に非公開情報が
入る余地はない。入りうるのは次の5つに限られる。

1. 台帳の実体（抽出されたタスクの本文）
2. 外部サービスへの接続設定と識別子
3. 情報源側の命名規則（どのタスクがコンテナかを判別するための文字列）
4. テストフィクスチャ
5. 動作確認時の出力

1〜3は設計で追い出せる。4と5は人間の運用に依存する。とくに5は、実行結果を README や
issue、コミットメッセージに貼りたくなる動機が常に働くため、注意力だけでは守れない。

## Decision

コードは公開リポジトリに置く。そのうえで次を守る。

- 上記1〜3はすべて `~/.claude-secretary/` 配下に置き、リポジトリに含めない。
  リポジトリにはコードのみを置く
- テストフィクスチャは架空データのみとする。実データからの複製を禁じる
- 実データでの動作確認結果をリポジトリ内の文書・コミットメッセージに転記しない
- 上記の規律を人間の注意力に委ねず、リポジトリ全体を走査して組織固有の情報らしい
  パターンを検出するテストを置き、混入を機械的に落とす

## Consequences

- 既存の自作ツールと同じ導線で配布できる。他ツールを導入していない相手にも秘書だけを
  渡せる
- 実データに近いフィクスチャを書けないため、パーサのテストは構造の検証に限られる。
  実データとの乖離は手動の受け入れ確認で埋める必要がある
- 検出テストはパターンの列挙に依存する。想定外の形をした情報は素通りするため、
  完全な保証ではなく「典型的な事故を落とす網」と位置づける
- この判断を後から覆す場合、公開済み履歴からの除去は現実的でない。リポジトリを
  作り直すことになる。取り返しがつかない側の判断である
