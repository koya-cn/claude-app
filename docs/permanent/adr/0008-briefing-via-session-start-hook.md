# 0008. 起動時のブリーフィングをフックからの文脈注入で行う

- Status: accepted
- Date: 2026-09-09
- Deciders: リポジトリ所有者

## Context

台帳はできたが、中身を見る手段が生のJSONしかない。毎朝の棚卸しを成立させるには、
起動したときに「今やること」が目に入る必要がある。

Claude Code の `SessionStart` フックを使うつもりで挙動を確認したところ、決定的な事実が
2つ分かった。

**フックの標準出力は利用者の画面ではなく、モデルの文脈に注入される。** このマシンで既に
動いている同種のフックの実装（`session-start-s-t-dev-check.py`）がその前提で書かれており、
「stdout に書いた文字列が Claude の文脈に入る」と明記されている。つまりフック側で
人が読む形に整形しても、その整形物は誰の目にも触れない。

**フックからはコネクタを呼べない。** フックはシェルコマンドとして実行され、カレンダーや
ドライブへの到達手段はモデル側の道具である。したがって起動時に収集そのものを走らせる
ことはできず、フックにできるのは既にある台帳を読むことだけになる。

提示の頻度も論点だった。毎セッション出すと邪魔になる。フックが受け取る入力には起動の
種別を示す `source` が含まれるが、**取りうる値を確認できなかった**。このマシンの既存
フック4本のうち、`source` で分岐しているものは1つもない。

対案は3つあった。

ステータスラインに出す案。常に見えるが1行しかなく、複数のやり残しを並べる用途に合わない。

フック側で整形して標準出力に書く案。上記のとおり画面に出ないため、意味を持たない。

`source` の値で起動種別を判定して回数を絞る案。確認できていない値に依存する設計になる。

## Decision

起動時のブリーフィングは `SessionStart` フックで行う。フックの責務は次の3つに限る。

- 台帳から提示に必要な材料を取り出す（整形はしない）
- それをモデルへの指示とともに標準出力へ書き、文脈に注入する
- 提示の頻度を最終提示日で制御する

**整形はモデルに任せる。** 台帳の読み手は人ではなくモデルである、という第1スライスからの
方針（`list` が生のJSONを出すこと）をそのまま延長する。

**提示の頻度は最終提示日をファイルに持って比較する。** 起動の種別には依存しない。
同じ日に何度起動しても最初の1回だけ提示する。週の初回は週次の形にする。

**収集はフックから走らせない。** 台帳が古い場合は、収集を促す指示を文脈に載せるに
とどめる。実際に走らせるかは利用者とモデルが決める。

## Consequences

- フックが軽い。台帳を1つ読むだけなので、起動を待たせない
- 提示の形をモデルが決めるため、状況に応じて変えられる。反面、**毎回同じ形で出る保証が
  ない**。決まった形で出したいなら指示文で縛る必要がある
- 起動種別に依存しないので、`--resume` や `/clear` の後に何度起動しても増えない。
  ただし**日付が変わるまで再提示できない**ため、意図して見直したい場合の経路が別に要る
- 収集が自動で走らないので、**放置すると台帳が古いまま提示され続ける**。台帳の最終更新から
  日が経っていることを提示に含めて、人が気づけるようにする
- `source` の値は未確認のまま残る。将来「起動時だけ」「再開時は出さない」といった区別が
  必要になった時点で確認することになる
- フックの標準出力が文脈に入るという挙動は、このマシンで動いている実装から確認した。
  公式ドキュメントでの裏取りはしていない（確認しようとしたが利用上限に当たった）。
  挙動が変わればブリーフィングは静かに出なくなる
