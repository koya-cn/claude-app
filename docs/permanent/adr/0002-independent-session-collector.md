# 0002. セッション収集を既存ツールに依存せず専用実装にする

- Status: accepted
- Date: 2026-09-04
- Deciders: リポジトリ所有者

## Context

同じリポジトリの既存ツールに、未完了セッションを検出する機能が既にある。秘書が必要と
するものと目的が重なるため、再利用すべきかを検討した。

実行して確認したところ、次の状態だった。

- 検出は、末尾のAI発話に対して「やり残しを示す語句」を照合する方式。単なる状況説明や
  手順説明が引っかかり、誤検出が多い
- 機械可読な出力を持つのはブラウザUI用のHTTP APIだけで、コマンドラインの出力は
  人間向けの整形テキストのみ
- プルリクエストのマージ状態判定と、LLMによる分類は、いずれもブラウザUI経由でしか
  呼べない
- 単一ファイル3430行に対してテストが1件も存在しない

対案は、既存ツール側に機械可読な出力を追加し、検出ロジックもそこで作り直して、秘書は
それを消費する形だった。本家への還元になり、マージ状態判定を再実装せずに済む利点がある。

判断材料として、過去に別の機能が既存ツールの整形テキストをパースする方式を採ったものの、
後に専用の収集スクリプトへ置き換えられている事実があった。人間向け出力への依存は一度
試して捨てられている。

## Decision

秘書は専用のセッション収集を持ち、セッション記録を直接読む。既存ツールには依存しない。

## Consequences

- テストが存在しない巨大なファイルを触らずに済む。秘書側はテストを最初から積める
- 既存ツールを導入していない環境にも、秘書単体で配れる
- 検出ロジックが二重になる。既存ツール側の検出は低精度のまま残り、どちらの結果が正しいのか
  が利用者から見て曖昧になる
- マージ状態の判定は秘書側で再実装が必要になる
- 秘書側の検出が安定した段階で既存ツールへ移植する余地は残る。ただし移植が実行されない
  まま重複が固定化するリスクを織り込む
